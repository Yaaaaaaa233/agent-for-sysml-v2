## 1. 通用约定

### 1.1 编码与整体骨架

- UTF-8、LF 换行；文件末尾保留一个换行。
- 生成文本由 `package <package> { ... }` 包裹，`package` 名来自 IR 顶层 `package`。
- 可选两行生成器头注释（`include_header=true`，默认开）。
- **package 内固定两行标准库 import**（位置与缩进定死，紧跟 `package` 行、先于任何分节）：

```sysml
// Generated by sysml-modeling-agent - schema sysml-ir/v1.
// Source of truth is the IR JSON; regenerate with generate_sysml. Do not edit by hand.
package CoaxialOctoRotor {
    private import ScalarValues::*;
    private import SI::*;

    // ---- PartDefinition ----
```

  这两行不是 IR 字段，而是渲染常量（`generator.STANDARD_IMPORTS`）：官方实现把 `Real` /
  `String` / SI 单位当作需要解析的名字，缺 import 时会报引用错误；`private` 是本版官方语法
  的实测要求（裸 `import` 被拒绝，见 EVIDENCE §9.3）。逆解析时识别并跳过它们，不进 IR；
  任何**其它** import 不在本子集内，`parse_sysml` 会记 `unsupported`。
  缩进与其它 package 体成员一致：默认 4 个空格，随 `generate_sysml(indent=...)` 变化；
  位置固定在 `package ... {` 之后、第一条分节标题之前，中间不插空行（分节标题自己带空行）。

- 缩进单位默认 4 个空格，可由 `generate_sysml(indent=...)` 配置；缩进只影响可读性，
  不参与语义。

### 1.2 确定性

同一份 IR JSON 必得逐字节相同的文本（`sha256` 相同）。为此：

- 元素按 **owner 关系嵌套**；
- 同一 owner 下先按 `KIND_ORDER` 分组，再按元素 `id` 升序；
- 声明体内部按固定字段顺序渲染（见各 kind）；
- 所有集合不依赖 JSON 对象键序。

`KIND_ORDER`（也是 package 级分节标题的顺序）：

```
PartDefinition → PartUsage → Requirement → ActionDefinition
→ StateDefinition → Attribute → Constraint → Connection
```

### 1.3 两种名字

- **IR `id`**（如 `REQ-CRUISE-ENDURANCE`、`PART-USE-ESC`）只出现在 JSON 与
  `//` 注释（`// id:`、追溯关系、Connection 标注）里，**不**直接当 SysML 标识符。
- **`name`**（如 `CruiseEndurance`、`escUnit`）落进文本当标识符，必须匹配
  `^[A-Za-z_][A-Za-z0-9_]*$`。
- 文本里引用另一个元素时（`PartUsage.typeRef`、`Constraint.parameters`、
  `Connection.sourceRef/targetRef`），渲染该元素的 **`name`**，而不是 `id`。

### 1.4 声明形态与分节

- 无体元素：`<signature>;`
- 有体元素：`<signature> {` … `}`；体内每行按缩进渲染。
- package 级每个 kind 前插入空行与分节标题：

```sysml
    // ---- PartDefinition ----
```

- 每个元素声明前固定先输出一行 `// id: <id>`（`Connection` 除外，它的 id 在结构化注释里）。
  这是 v2 逆解析能完整还原 IR 的**唯一**依据：文本里的声明只带 `name`，而 IR 以 `id` 为键。
- 元素级 `description` 渲染在 id 之后、声明**前一行**的结构化注释：

```sysml
    // id: PART-BATTERY-PACK
    // description: 动力锂电池包，为整机提供能量。
    part def BatteryPack {
```

  顺序固定：`// id:` 在前，`// description:` 在后；两者都属于紧随其后的那条声明。

  `description` 中的换行会被折叠为空格，`*/` 会被替换为 `* /`，保证不会提前闭合注释。

### 1.5 注释与字符串的边界

- 所有非正式语法的元信息一律走 `//` 行注释；`doc /* ... */` 只用于 Requirement 的正文与验收判据。
- 字符串字面量用 JSON 转义（`json.dumps(..., ensure_ascii=False)`），因此中文保持原样。
- 注释内容不得跨行：generator 会把换行折叠为空格。

## 2. 八种 kind 的渲染形态

下文的 `<name>` 一律指 IR `name`；引用类字段会先解析成被引用元素的 `name`。

### 2.1 `PartDefinition` —— 结构定义

| IR | 文本 |
| --- | --- |
| `name` | `part def <name>` |
| `properties.isAbstract == true` | 前缀 `abstract ` |
| 有子元素 / relations | `{ ... }` 体；否则 `;` |
| `properties.description` | 声明前一行 `// description: ...` |

```sysml
part def BatteryPack;
abstract part def PowerSource {
    // ...
}
```

逆解析：`\b(?:abstract\s+)?part\s+def\s+([A-Za-z_][A-Za-z0-9_]*)`。

### 2.2 `PartUsage` —— 结构用法

模板：

```text
part <name> : <typeRef 的 name>[<quantity>];        # quantity 存在
part <name> : <typeRef 的 name>;                    # quantity 不存在
```

- `quantity` **存在就渲染** `[n]`，**包括 `n = 1`**；不存在则完全不加后缀。
  `quantity` 是数字（IR 层校验），整数渲染为 `1` / `8`，浮点按原值渲染。
- 有子元素或 relations 时把 `;` 换成 `{ ... }`：

```sysml
part escUnit : ElectronicSpeedController[8] {
    // 追溯关系 (relations):
    //   PART-USAGE-ESC --connects--> PART-USAGE-MOTOR-UPPER  (电调按转速指令驱动上桨电机)
}
```

逆解析：先用 `\bpart\s+([A-Za-z_][A-Za-z0-9_]*)\s*:\s*([A-Za-z_][A-Za-z0-9_]*)`
取名字与类型，再用后缀正则 `\[([^\[\]\r\n]+)\]\s*(?:;|\{)` 取多重度。

> 本约定只支持单一数字多重度；`[0..*]`、`[1..4]` 等区间形态**未定义**，IR 也不接受。

### 2.3 `Requirement` —— 需求

```sysml
requirement def <name> {
    doc /* <properties.text> */
    doc /* 验收判据: <properties.acceptanceCriteria> */
    attribute verifyMethod : String = "<verifyMethod>";
    attribute priority : String = "<priority>";
    attribute source : String = "<source>";
    attribute rationale : String = "<rationale>";
    attribute <阈值字段> : <Real|Integer|Boolean> = <值>;
    // 追溯关系 (relations):
    //   <id> --<type>--> <targetId>  (<rationale>)
}
```

- 固定顺序：`verifyMethod`、`priority`、`source`、`rationale`（存在才渲染）。
- 其余非保留字段按字段名升序渲染为阈值 `attribute`；`{value, unit}` 形态渲染为
  `attribute x : Real = <value> [<unit>];`。
- `description` 仍渲染为声明前的 `// description:`。

逆解析：`\brequirement\s+def\s+(...)`；体内 `doc /* ... */` 与 `attribute` 行按
`scopeKind == Requirement` 区分——这些阈值 `attribute` **不是**独立 IR 元素。

### 2.4 `ActionDefinition` —— 功能 / 动作

```sysml
action def <name> {
    in <portName> : <typeRef>;  // unit: <unit>
    out <portName> : <typeRef>;  // unit: <unit>
}
```

- `inputs` 先于 `outputs`；端口顺序保持 IR 数组顺序。
- 端口 `unit` **仍以行内注释承载**（`// unit: ...`）。本次三处语法升级只覆盖
  `Attribute.unit`、`PartUsage.quantity`、`StateDefinition.transitions`；
  Action 端口单位是否也有对应正式记法，待官方解析器/样本模型回验后再定，**不臆造**。

逆解析：`\baction\s+def\s+(...)`，`in`/`out` 行按关键字提取；端口单位注释可忽略。

### 2.5 `StateDefinition` —— 状态机

采用官方 Pilot Implementation 实测可接受的记法（初始态 `entry; then ...;`、迁移
`transition <name> first ... then ...;`）：

```sysml
state def <name> {
    entry; then <initial>;                              # initial 存在时
    state <state1>;
    state <state2>;
    // trigger: <trigger>                               # trigger 存在时（结构化注释）
    transition <合成名> first <from> [if (<guard>)] then <to>;
}
```

- 顺序固定：先 `entry; then <initial>;`（若有），再按 IR `states` 数组顺序渲染所有
  `state`，最后按 IR `transitions` 数组顺序渲染迁移。
- **初始态**：官方记法 `entry; then <state>;`（不是 `initial <state>;`）。
- **迁移名**：官方语法要求 `transition` 后跟名字，而 IR 的 `transitions[]` 没有名字，
  因此合成 `Transition_<from>_to_<to>_<index>`（`index` 为在 `transitions` 数组中的下标），
  保证确定性且同一状态机内不重名；逆解析时这个名字**不还原**进 IR。
- **guard**：存在且非空白 → 在 `first ...` 之后加 `if (<guard>)`；否则整段省略。
- **trigger**：IR 里是自由文本（如 `start command`），官方 `accept` 需要可解析的
  信号/事件类型，直接塞进语句会产出无法解析的文本。因此 trigger 以**结构化注释**
  `// trigger: <trigger>` 放在迁移语句上一行；没有 trigger 时不产生该注释。
  guard 仍写进正式语句（它本身就是布尔表达式）。
- trigger / guard 内的换行折叠为空格。

```sysml
state def MotorStates {
    entry; then Idle;
    state Idle;
    state Running;
    // trigger: start command
    transition Transition_Idle_to_Running_0 first Idle if (rpm > 1000) then Running;
}
```

> **回验证据（2026-10-17）**：用官方 Pilot Implementation 后端解析上述形态
> （`entry; then Idle;`、`transition T first Idle if (...) then Running;`）返回 **0 error**；
> 在补齐 §1.1 的标准库 import 头之后，本项目 `base_model` / `extended_model` 生成文本
> 整体也是 **0 条诊断**（EVIDENCE §13）。这不等于「整体模型已通过官方验证」，
> 只说明本节的语法形态与引用解析被官方解析器接受；语义与建模质量未验证。
>
> 若后续确认更贴切的官方写法，允许调整模板，但必须同步更新本文件、`sysml_lint`
> 的逆解析与测试，保持可逆。

逆解析：

- 声明：`\bstate\s+def\s+([A-Za-z_][A-Za-z0-9_]*)`；
- 初始态：`^entry\s*;\s*then\s+([A-Za-z_][A-Za-z0-9_]*)\s*;$`；
- 状态：`^state\s+([A-Za-z_][A-Za-z0-9_]*)\s*;$`（排除 `state def`）；
- 迁移：`^transition\s+(\w+)\s+first\s+(\w+)(?:\s+if\s*\((.*)\))?\s+then\s+(\w+)\s*;$`；
- trigger：迁移上一行的 `^//\s*trigger:\s*(.*)$`。

### 2.6 `Attribute` —— 数值属性（参数）

模板：

```text
attribute <name> : <valueType> = <defaultValue> [<unit>];
attribute <name> : <valueType> = <defaultValue>;
attribute <name> : <valueType>;
```

示例：

```sysml
attribute cruisePowerW : Real = 240.0 [W];
attribute speedRatioEta : Real = 1.0;
```

- `defaultValue` 存在才渲染 `= ...`；类型必须与 `valueType` 匹配（IR 层校验）。
- `unit` 存在且非空 → 追加 ` [<unit>]`；不存在则**不加后缀**。
- 单位内容内部空白折叠为单个空格（如 `m / s` → `m / s`）；不加引号。
- **单位别名**：官方标准库没有 `Wh`（实测，EVIDENCE §8.4），因此渲染时把 IR 的 `Wh`
  映射为等价表达式 `W*h`（`generator.UNIT_ALIASES`）；逆解析按同一张表反向还原成 `Wh`。
  往返稳定：IR `Wh` → 文本 `W*h` → IR `Wh` → 文本 `W*h`（逐字节一致）。
  映射只对**整串恰好等于别名左侧**的单位生效；其它单位原样渲染。若 IR 里本来就写 `W*h`，
  逆解析会把它规范化为 `Wh`——这是别名的已知单向归一化，见 §5 第 9 条。
- Requirement 阈值里的 `{value, unit}` 走同一后缀规则，见 2.3。

逆解析：`\battribute\s+([A-Za-z_][A-Za-z0-9_]*)\s*:\s*([A-Za-z_][A-Za-z0-9_]*)`，
后缀正则取 `unit`；默认值按 `= ... [unit];` 切分。

### 2.7 `Constraint` —— 参数约束 / 公式

`Constraint` 是正式元素，但公式与参数列表暂用**结构化注释**承载在 `constraint def` 体内：

```sysml
    // description: 续航换算约束：电池可用能量除以巡航功率得到续航时间。
    constraint def EnduranceBudget {
        // expression: T = batteryCapacityWh * usableEnergyFraction / cruisePowerW
        // parameters: batteryCapacityWh, usableEnergyFraction, cruisePowerW, enduranceHours
        // 追溯关系 (relations):
        //   CONSTRAINT-ENDURANCE-BUDGET --satisfiedBy--> PART-POWER-CHAIN  (示例)
    }
```

规则：

- 签名固定 `constraint def <name>`，必有体（至少 expression 与 parameters 两行）。
- `expression`：**单行**非空公式文本，IR 校验禁止 `\r`/`\n`；generator 渲染前把换行折叠为空格。
- `parameters`：至少 1 项，IR 里是元素 `id` 数组；渲染为**被引用 Attribute 的 `name`**，
  按数组顺序用 `", "` 连接。
- 两行注释顺序固定：`// expression:` 在前，`// parameters:` 在后。
- `relations` 追溯注释照常渲染在其后。
- `description` 仍渲染为声明前的 `// description:`。

逆解析：

1. 用 `\bconstraint\s+def\s+(...)` 取声明与块范围；
2. 块内 `^//\s*expression:\s*(.*)$` 取公式；
3. 块内 `^//\s*parameters:\s*(.*)$` 按逗号切分取参数名；
4. 参数名 → Attribute 的 `id` 需要 IR 的名字映射（文本里没有 id）。

### 2.8 `Connection` —— 两个 PartUsage 之间的连接

`Connection` 在 **owner 块内**渲染为「结构化注释 + `connect` 语句」：

```sysml
        // Connection CONN-BATTERY-ESC flowKind=electrical name=batteryToEsc description: 电池直流母线馈入八路电调。
        connect batteryPack to escUnit;
```

规则：

- 结构化注释固定前缀 `// Connection `，随后是 IR `id`、` flowKind=<flowKind>`、
  ` name=<name>`（v2 新增：`connect` 语句没有名字位置，不再落盘就无法还原 IR 的 `name`）。
- `description` 存在且非空 → 在同一行追加 ` description: <description>`；否则不追加。
- 字段顺序固定：`id` → `flowKind` → `name` → 可选 `description`。
- 下一行固定 `connect <sourceRef 的 name> to <targetRef 的 name>;`。
- `Connection` 自身的 `name` 由结构化注释里的 `name=` 承载（`connect` 语句没有名字位置）；
  旧手写文本可省略，`parse_sysml` 会合成一个确定性名称并记 warning。
- 若 `Connection` 带 `relations`，其追溯注释渲染在 `connect` 语句之后。
- `Connection` 的 owner 决定它出现在哪个块里；两端 `PartUsage` 必须与它同 owner（IR 校验）。

> 区分：`Connection` 是 **kind**（正式连接元素）；`relations[].type = "connects"` 是另一套
> **追溯注释**（电池用法 connects 到电调用法）。两者可以并存，语义不同，不要互相替代。

逆解析：

1. 扫描 `^//\s*Connection\s+([A-Za-z_][A-Za-z0-9_-]*)\s+flowKind=([A-Za-z_][A-Za-z0-9_]*)(?:\s+name=([A-Za-z_][A-Za-z0-9_]*))?(?:\s+description:\s*(.*))?$`；
2. 跳过空行，下一行必须是 `^connect\s+(\w+)\s+to\s+(\w+)\s*;$`；
3. 用注释里的 `id` 与 IR 对齐；两端 name 通过 IR 名字映射还原成 id。

格式错误由 lint 报 `L008`；注释后没有 `connect` 语句报 `L009`。

## 3. 注释格式总表

| 注释 | 出现位置 | 格式（正则） | 用途 |
| --- | --- | --- | --- |
| 生成器头 | 文件开头（可选） | `^// Generated by sysml-modeling-agent` | 溯源，不参与语义 |
| 标准库 import | package 内固定两行 | `^private import (ScalarValues|SI)::\*;$` | 标准库解析；逆解析跳过，不进 IR |
| 分节标题 | package 级 | `^// ---- <Kind> ----$` | 可读性，可忽略 |
| 元素 id | 声明前一行 | `^// id: ([A-Za-z_][A-Za-z0-9_-]*)$` | 还原 IR `id`（`Connection` 走标注行） |
| 描述 | id 之后、声明前一行 | `^// description: (.*)$` | `properties.description` |
| 追溯关系标题 | 元素体内 | `^// 追溯关系 \(relations\):$` | 固定标题 |
| 追溯关系项 | 标题后 | `^//   (\S+) --(\w+)--> (\S+)  \((.*)\)$` | `relations[]` |
| Constraint 公式 | `constraint def` 体内 | `^// expression: (.*)$` | `Constraint.expression` |
| Constraint 参数 | 公式之后 | `^// parameters: (.*)$` | `Constraint.parameters` |
| 迁移 trigger | transition 上一行 | `^// trigger: (.*)$` | `transitions[].trigger`（guard 在语句里） |
| Connection 标注 | `connect` 上一行 | `^// Connection (\S+) flowKind=(\w+)(?: name=(\w+))?(?: description: (.*))?$` | `Connection` 的 id / flowKind / name / description |

追溯关系项的语义：`<源元素 id> --<relation type>--> <目标元素 id>  (<rationale>)`；
它是**注释**，不产生 SysML 声明，也不要被逆解析当成元素。`relations` 为空时不渲染标题。

## 4. IR 字段 → 文本总表

## 5. 已知限制（必须如实告知调用方）

1. **语法与引用解析 0 error，但语义/建模质量未验证**（见 §0、§2.5）：
   2026-10-17 用官方 Pilot Implementation 实测 golden / base / extended 三份生成文本，
   均为 0 条诊断（证据：`docs/probe-official-parser/EVIDENCE.txt` §13）。这一结论的
   范围**仅限**「官方实现接受这些语法形态并解析了其中的名字/引用」；它不评估语义正确性、
   参数合理性或建模质量，也**不得**被写成整体性的「已通过官方解析器验证」。
   `lint_sysml` 只做结构自查，不做 SysML 语义校验，也不等同于官方解析器。
2. **`Constraint.expression` 是自由文本**，不解析、不计算、不做量纲检查；参数与公式中的符号
   是否真的对应，语义工具无法保证。
3. **`Connection` 只表达两端 PartUsage 的连接**，不表达端口（port）、方向、流量属性。
4. **多重度只支持单一数字**，不支持 `[1..4]` / `[0..*]`。
5. **Action 端口 unit 仍为注释**，与 Attribute 的单位后缀不统一，待回验后统一。
6. `Connection` 的 `name` 依赖结构化注释里的 `name=`；若外部手改文本删掉整行注释，
   `connect` 语句将无法还原出 IR 的 Connection 元素（lint 会报 `L009`）。缺 `name=`
   但保留 id/flowKind 时，`parse_sysml` 会合成确定性 name 并记 warning。
7. 本文件是**项目内约定**，不是 OMG 规范文本；规范语义以官方规范为准，推断部分不得当作定论。
8. 文本里只保留被引用元素的 `name`（`Constraint.parameters`、`Connection` 两端、`PartUsage.typeRef`），
   逆解析要靠 IR 的 name → id 映射。`parse_sysml` 的口径是「**同 owner 优先，其次全局唯一**」；
   仍然歧义时报 `E-PARSE-AMBIGUOUS`，解析不到报 `E-PARSE-UNRESOLVED`，不猜测。
9. **单位别名单向归一化**：IR 里的 `Wh` 渲染为 `W*h`，逆解析把 `W*h` 还原为 `Wh`。
   若 IR 本来就把单位写成字面量 `W*h`，经一次 parse 会变成 `Wh`（元素级不再与原 IR 全等）；
   这是别名机制的已知边界，当前标杆/演示模型的规范写法是 `Wh`。
10. **文本不是无损容器**：`description` / `doc` / trigger / expression 等自由文本在渲染时
   会把换行折叠为空格（`description` 还会把 `*/` 转成 `* /`），逆解析无法还原折叠前的原文。
   另外，「显式 `isAbstract: false`」与空字符串 `description` / `unit` / `guard` / `trigger`
   在文本里没有对应写法，逆解析不会还原这些键。元素级往返一致的前提是这些字段本身是
   「单行、无 `*/`、非空」。
11. **`Real` 的字面量类型**：generator 对 `Real` 一律渲染成带小数点的形式；若 IR 的
   `defaultValue` 写成整数（如 `24`），parse 会得到 `24.0`，元素级比较会看到数字类型差异。
   规范做法是按 `valueType` 写 `24.0`（`Attribute` 层校验也会提示类型匹配）。
12. **`parse_sysml` 只解析本文件定义的子集**，不是完整 SysML v2 语言解析器。子集外构造
   （`item` / `port` / `satisfy` / 裸 `import` / 多行块注释等）不崩溃、不静默：逐条进
   `unsupported`（带行号）并令 `ok=false`；解析器也**不代替** `validate_model_json`。
13. **`requirement def` 体内的 `attribute` 一律按需求字段/阈值解析**。如果 IR 把某个
   `Attribute` 元素的 owner 设成 `Requirement`，它的渲染形态与阈值字段完全相同，
   逆解析不会把它还原成独立元素。规范建模应把可复用参数放在部件/包下。

## 6. 最小示例（覆盖三种新语法 + 两种新 kind）

IR（节选）：

```json
{
  "schema": "sysml-ir/v1",
  "package": "Demo",
  "elements": [
    { "id": "PART-DEF-MOTOR", "kind": "PartDefinition", "name": "Motor", "owner": "Demo", "properties": {} },
    { "id": "PART-USE-MOTOR", "kind": "PartUsage", "name": "motorOne", "owner": "Demo",
      "properties": { "typeRef": "PART-DEF-MOTOR", "quantity": 4 } },
    { "id": "PART-USE-MOTOR-TWO", "kind": "PartUsage", "name": "motorTwo", "owner": "Demo",
      "properties": { "typeRef": "PART-DEF-MOTOR", "quantity": 4 } },
    { "id": "ATTR-V", "kind": "Attribute", "name": "ratedVoltage", "owner": "Demo",
      "properties": { "valueType": "Real", "defaultValue": 24.0, "unit": "V" } },
    { "id": "C-1", "kind": "Constraint", "name": "VoltageLimit", "owner": "Demo",
      "properties": { "expression": "V <= 26.0", "parameters": ["ATTR-V"] } },
    { "id": "CONN-1", "kind": "Connection", "name": "motorLink", "owner": "Demo",
      "properties": { "sourceRef": "PART-USE-MOTOR", "targetRef": "PART-USE-MOTOR-TWO", "flowKind": "electrical" } }
  ]
}
```

生成文本（节选）：

```sysml
package Demo {
    private import ScalarValues::*;
    private import SI::*;

    // ---- PartDefinition ----
    // id: PART-DEF-MOTOR
    part def Motor;

    // ---- PartUsage ----
    // id: PART-USE-MOTOR
    part motorOne : Motor[4];
    // id: PART-USE-MOTOR-TWO
    part motorTwo : Motor[4];

    // ---- Attribute ----
    // id: ATTR-V
    attribute ratedVoltage : Real = 24.0 [V];

    // ---- Constraint ----
    // id: C-1
    constraint def VoltageLimit {
        // expression: V <= 26.0
        // parameters: ratedVoltage
    }

    // ---- Connection ----
    // Connection CONN-1 flowKind=electrical name=motorLink
    connect motorOne to motorTwo;
}
```
