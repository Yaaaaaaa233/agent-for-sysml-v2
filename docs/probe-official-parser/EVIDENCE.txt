§0 一页结论
================================================================================

- 官方解析器可用：`org.omg.sysml.interactive.SysMLInteractive`（EPL-2.0）在本机 JRE 21 上
  启动正常，加载官方标准库 94 个文件，能对输入文本给出带行号的 error/warning。
- 阳性对照通过：带 `private import ScalarValues::*;` 的最小模型 -> 0 error（§9）。
- 官方自带示例通过：`VehicleDefinitions.sysml`（官方 SysML-v2-Release 2026-08）-> 0 error，
  说明「启动 + 标准库 + 喂文本」这条链路本身是有效的，不是驱动方式坏了。
- 本项目标杆文本 **未通过** 官方语义校验：0 语法错误 / 77 语义错误 / 9 warning（§6）。
  两类根因（§8 有对照实验）：
    a. 生成器不输出 `import`：`Real`（24 次）、`String`（12 次）解析不到，
       连带 `An attribute must be typed by attribute definitions.`（29 次）、
       `A usage must be typed by definitions.`（7 次）。
    b. 单位写法 `[...]` 里的 `Wh` 在官方标准库中不存在（`W`/`h`/`m`/`s` 都在 SI 里）。
       补 `private import ScalarValues::*;` + `private import SI::*;` 后只剩 1 条错误：`Wh`。
- 本机原先没有 JVM（§1）；现在的 JVM 是本 spike 下载到本目录的 Temurin JRE 21，
  不入 git（`.gitignore`），复现方式见 §3、§10。

§2 在线调研：官方发行形态与许可证
================================================================================

仓库：https://github.com/Systems-Modeling/SysML-v2-Pilot-Implementation
最新 release：tag `2026-08`，published 2026-09-11T20:08:19Z
  https://github.com/Systems-Modeling/SysML-v2-Pilot-Implementation/releases/tag/2026-08
许可证：Eclipse Public License - v 2.0（EPL-2.0）
  LICENSE 首行：`Eclipse Public License - v 2.0`
  该 release 说明也明确：语言与 API 实现已从 LGPL 改为 EPL 分发。
  库模型（sysml.library / *.kpar）随该 release 一并分发。

release 资产（2026-08）关键项：
  jupyter-sysml-kernel-0.62.0.zip   126,136,336 B   <- 本 spike 采用
  jupyterlab-sysml-0.62.0.tgz             5,082 B
  Kernel_*.kpar / SysML_*.kpar         2 KB ~ 153 KB（标准库的 KPAR 打包）
  （SysML-v2-Release 仓库另有 install/eclipse/org.omg.sysml.site.zip，43,995,101 B）

**没有 standalone 的 parser jar / 命令行二进制。** 官方只发布两种可运行形态：
  1) Eclipse 插件（OSGi bundle 集合，headless 驱动成本高）；
  2) Jupyter kernel 发行包（一个 fat jar + 标准库 + kernel.json）。

kernel 的启动方式（官方 kernel.json 原文）：
  {
    "argv": ["java", "-cp", "@KERNEL_INSTALL_DIRECTORY@/*",
             "org.omg.sysml.jupyter.kernel.ISysML", "{connection_file}"],
    ...
  }
即：官方自己也是用 `java -cp <目录>/*` 起 JVM。

本适配层选用的入口（同一个 fat jar 里就有）：
  org.omg.sysml.interactive.SysMLInteractive
  main(String[] args)：args[0] = 标准库目录（`loadLibrary`），随后进入 REPL 读 stdin。
  源码：org.omg.sysml.interactive/src/org/omg/sysml/interactive/SysMLInteractive.java
  （main 在第 856 行附近；`loadLibrary` 读 `<path>/Kernel Libraries`、`Systems Library`、
   `Domain Libraries` 三个子目录）

REPL 的多行输入约定（源码 run() 里可见）：
  - 单独一行 `%` 进入多行输入模式，读到下一个单独一行 `%` 为止，整段作为一次 parse；
  - `%exit` 退出。
适配层据此把待解析文本包成 `% ... % %exit` 喂进去（见 §5）。

§4 原始启动命令（不经适配层，直接喂官方 REPL）
================================================================================

在仓库根执行：

# 4.1 生成 REPL 输入：单独一行 % 包住文本，再以 % / %exit 收尾
$ .venv/bin/python -c 'import sys; t=open(sys.argv[1],encoding="utf-8").read(); sys.stdout.write("%\n"+t+"\n%\n%exit\n")' \
    examples/golden-coaxial-power-chain/golden-coaxial-power-chain.sysml > /tmp/golden.in

# 4.2 启动官方交互式入口（注意：标准库参数必须是**绝对路径**）
$ docs/probe-official-parser/jre/Contents/Home/bin/java -Xmx1024m -Djava.awt.headless=true \
    -cp "docs/probe-official-parser/kernel/*" \
    org.omg.sysml.interactive.SysMLInteractive \
    "$PWD/docs/probe-official-parser/kernel/sysml.library" < /tmp/golden.in

踩过的坑（都有据可查，写下来省后来人时间）：
- 标准库路径**不能给相对路径**。给 `kernel/sysml.library` 时 EMF 的 `URI.createFileURI`
  会把子目录名里的空格编码成 `%20` 并当成真实文件名去找，直接
  `FileNotFoundException: .../Kernel%20Libraries/...`；给绝对路径则正常（§6 即绝对路径）。
- 文本结尾**必须换行**，否则结束标记 `%` 会和最后一行粘在一起，REPL 停在多行输入模式等
  EOF/下一行，表现为“卡死”。适配层用 `text.rstrip("\n") + "\n"` 固定处理。
- 本版语法**不接受裸 `import`**（实测，见 §9.3）。

【模型事实】（这些是命令输出里直接可数的）
- 0 条语法错误：输出里没有 `no viable alternative` / `mismatched input` / `extraneous input`
  / `missing EOF` 这类 Xtext 语法诊断。
- 77 条 ERROR，按原文分类计数（相加正好 77）：
    29  An attribute must be typed by attribute definitions.
    24  Couldn't resolve reference to Type 'Real'.
    12  Couldn't resolve reference to Type 'String'.

     5  Couldn't resolve reference to Element '...'：
          'W'（1）、'h'（1）、'm'（1）、's'（1）、'Wh'（1）
  小提示：第一条 ERROR 与 REPL 提示符粘在同一行（`1> ERROR:...`），所以若用 `grep ^ERROR`
  逐行统计会少 1 条（Real 显示 23）；正确总数是 77。适配层会先剥掉 `N> ` 前缀再统计。
- 9 条 WARNING，全部围绕 `[W] [h] [m/s]` 这类单位写法：
    `WARNING:Should be a measurement reference (unit).`
    `WARNING:Bound features should have conforming types`
- 退出码 0（REPL 正常退出，`%exit` 生效）。

【规范语义】（官方实现怎么判，不掺我的解释）
- 官方实现把 `Real` / `String` 当作**需要解析的引用**：没有 `import ScalarValues::*;`
  就报 `Couldn't resolve reference to Type`，并连带把使用它们的属性判成
  “must be typed by attribute definitions”。
- `attribute x : Real = 1200.0 [Wh];` 这种 `[...]` 写法被官方**语法**接受（无语法错误），
  但 `Wh` 被当作要解析的名字；`W`/`h`/`m`/`s` 能在 SI 库里找到，`Wh` 找不到。
- 因此：**语法合规 ≠ 语义合规**。本项目内置 lint 只能保证前者的一部分。

【推断】（我的判断，标明是推断）
- 77 条错误里绝大多数是“缺 import”这一条根因的连锁反应，不是 77 个独立缺陷；
  §8 的对照实验支持这个判断（补 import 后 77 -> 5 -> 1）。
- `Wh` 缺失说明标杆模型用了一个官方标准库没有的单位名。要么改用库里有的写法
  （例如 `W` 与 `h` 的组合，或在模型里自定义单位），要么在模型内声明 `Wh`。
  这一条需要建模负责人拍板，不属于适配层能修的范围。

§11 卡点与限制（诚实清单）
================================================================================

1. 本机原先**没有 JVM**（§1）。现在的 JVM 是 spike 下载到本目录的 Temurin JRE 21，
   不入 git；换机器/CI 必须重下，否则适配层只能返回 unavailable。
2. 官方**没有 standalone parser jar/CLI**（§2）。本适配层用的是 Jupyter kernel 发行包里的
   `SysMLInteractive` 交互式入口 + REPL `%` 多行输入，属于“官方组件的非官方用法”。
   它能给出与 Jupyter kernel 相同的 parse/validate 结果（kernel 内部同样调用
   `SysMLInteractive.process`），但不是官方文档承诺的 CLI 契约；官方若改 REPL 交互，
   本层要跟着改。
3. `%` 行冲突：文本里出现“单独一行 %”时，本层拒绝解析（status=unverified），
   不冒截断后误报通过的风险。
4. 官方实现每次启动都要重新加载 94 个库文件（本机约 4–6 秒），没有常驻进程/缓存。
   60 s 超时对本仓库规模足够，但批量解析大模型时会慢。
5. 只验证了 macOS arm64 + Temurin 21；Windows/Linux 未验证（适配层按路径/可执行名
   做了平台无关处理，但没有实测证据）。
6. **没有**把 official_parser 接进 verify_sysml / MCP 工具链（不在本任务文件范围）。
   目前它只是一个可独立调用的薄适配层。
7. 语义结论受“标准库版本”影响：本证据固定的是 kernel 0.62.0 / release 2026-08 的库。
8. 本证据只覆盖一个标杆文件；没有做更大语料的统计，不推广成“生成器整体合规率”。

14.3 本轮唯一影响文本形态的 IR 变化
  新增元素 STATE-FLIGHT-MODES（kind=StateDefinition，name=FlightModeStates，
  owner=CoaxialOctoRotor），渲染为：
        state def FlightModeStates {
            entry; then Takeoff;
            state Takeoff;
            state Cruise;
            state ReturnToHome;
            state Fault;
            state Landed;
            transition Transition_Takeoff_to_Cruise_0 first Takeoff then Cruise;
            // trigger: 返航指令或任务段剩余时间不足
            transition Transition_Cruise_to_ReturnToHome_1 first Cruise then ReturnToHome;
            // trigger: 转速比越界或功率遥测持续异常
            transition Transition_Cruise_to_Fault_2 first Cruise if (x8System.speedRatioEta <= 0.75) then Fault;
            // trigger: 触地检测（起落架受压）
            transition Transition_ReturnToHome_to_Landed_3 first ReturnToHome then Landed;
            // trigger: 迫降完成（触地检测）
            transition Transition_Fault_to_Landed_4 first Fault then Landed;
        }
  形态本身（entry; then / transition ... first ... [if (...)] then ...）已在 §13 实测过；
  本轮真正新增的实测点是 **guard 里的名字怎么才能被官方解析器解析**（见 14.4）。

14.4 guard 名字解析实验（同一后端，区分「通过」与「失败」两种写法）
  做法：复制 golden 的 StateDefinition，只改 owner 与 Cruise→Fault 的 guard，其余不变，
  生成后整份送官方后端。

    owner                 guard                             ok     诊断数  诊断摘要
    CoaxialOctoRotor      x8System.speedRatioEta <= 0.75    true   0       -
    CoaxialOctoRotor      speedRatioEta <= 0.75             false  1       Couldn't resolve reference to Element 'speedRatioEta'.
    CoaxialOctoRotor      enduranceHours <= 0.5              false  1       Couldn't resolve reference to Element 'enduranceHours'.
    CoaxialOctoRotor      faultDetected                     false  1       Couldn't resolve reference to Element 'faultDetected'.
    PART-STRUCT-SYSTEM    self.speedRatioEta <= 0.75        false  1       Couldn't resolve reference to Element 'speedRatioEta'.

  结论（范围限定）：本子集里 guard 只能引用**从 state def 所在作用域可达**的名字；
  包级 PartUsage 的特征要用点号路径（`x8System.speedRatioEta`）才解析得到，
  裸写特征名、或引用未定义标识符，都会新增 1 条诊断。golden 采用第一种（0 诊断）。
  这是「写得对才 0 error」的具体证据，不是「怎么写都行」。
