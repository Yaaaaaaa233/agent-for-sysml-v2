## 1. 演示前的模型（`demo/step0-before.ir.json`）

模型里已有 4 个元素：

| id | kind | 说明 |
| --- | --- | --- |
| `REQ-MISSION-ENDURANCE` | Requirement | 任务级续航（≥5.0 h），被功率链满足、被仿真工况验证 |
| `PART-POWER-CHAIN` | PartDefinition | 功率链定义 |
| `PART-USAGE-POWER-CHAIN` | PartUsage | 功率链的那一份实例 |
| `ACT-SIM-ENDURANCE` | ActionDefinition | 续航仿真工况，`verifies` 任务级续航 |

先确认它本身是干净的：

```
$ python3 mcp-server/run_server.py --call validate_model_json --input docs/demo/step0-before.ir.json
{
  "ok": true,
  "errors": [],
  "warnings": [],
  "schemaLayer": "unavailable",
  "counts": { "errors": 0, "warnings": 0 }
}
```

> `schemaLayer: "unavailable"` 是**如实汇报**：这台机器没装 `jsonschema`，第二层 JSON Schema
> 交叉检查没跑。核心规则是纯标准库实现，功能不减。

## 3. 第 2 步：LLM 产出 IR JSON（只填表，不写 SysML）

LLM 追加一个元素（字段形态对齐方案 2.3 的示例）。注意它**没有** `verifies` 关系——

```json
{

  "kind": "Requirement",
  "name": "CruiseEndurance",
  "owner": "CoaxialOctoRotor",
  "properties": {
    "text": "巡航时间不低于 4 小时",
```

## 4. 第 3 步：`validate_model_json` —— 校验，并且**读 warning**

```
$ python3 mcp-server/run_server.py --call validate_model_json --input docs/demo/step2-revised.ir.json
{
  "ok": true,
  "errors": [],
  "warnings": [
    {
      "code": "W-REQ-NO-VERIFY",
      "element": "REQ-CRUISE-ENDURANCE",
      "message": "该需求标注 verifyMethod=simulation，但尚未建立指向验证用例（仿真/试验）的 verifies 关系。",
      "pointer": "/elements/4/properties/verifyMethod"
    }
  ],
  "schemaLayer": "unavailable",
  "counts": { "errors": 0, "warnings": 1 }
}
```

**这一步是整个闭环的价值所在**：`ok=true`（结构合法，没有 error），但 warning 精确指出了
「这条需求声明了 `verifyMethod: simulation`，却还没有任何东西验证它」——
**这正是方案 2.3 第 2 步示例中预写的那条 warning 的原型。**

> 演示话术：「校验器不会因为我们写了个 JSON 就放过我们。它说：你标了要用仿真验证，
> **可谁去验证它？**——这条链现在是断的。」

## 6. 第 5 步：`generate_sysml` —— 确定性渲染

```
$ python3 mcp-server/run_server.py --call generate_sysml --input docs/demo/step4-final.ir.json
```

产物（存档 `demo/step5-generated.sysml`，41 行 / 1610 字符）：

```sysml
// Generated by sysml-modeling-agent - schema sysml-ir/v1.
// Source of truth is the IR JSON; regenerate with generate_sysml. Do not edit by hand.
package CoaxialOctoRotor {

    // ---- PartDefinition ----
    // description: 功率链：电池 → 电调 → 电机 → 桨。
    part def PowerChain;

    // ---- PartUsage ----
    part powerChain : PowerChain;

    // ---- Requirement ----
    requirement def CruiseEndurance {
        doc /* 巡航时间不低于 4 小时 */
        doc /* 验收判据: 在巡航速度 v 与转速比 eta 的稳态工作点下，满电续航时间 T >= 4.0 h */
        attribute verifyMethod : String = "simulation";
        attribute minEnduranceHours : Real = 4.0;
        // 追溯关系 (relations):
        //   REQ-CRUISE-ENDURANCE --refines--> REQ-MISSION-ENDURANCE  (由任务级续航需求分解而来)
        //   REQ-CRUISE-ENDURANCE --satisfiedBy--> PART-POWER-CHAIN  (由功率链（电池→电调→电机→桨）的设计参数保障)
    }
    requirement def MissionEndurance {
        doc /* 任务级续航：共轴八旋翼须按指定任务剖面完成起飞、巡航与安全返航。 */
        doc /* 验收判据: 在标称任务剖面下，全程可用飞行时间 T_mission >= 5.0 h。 */
        attribute verifyMethod : String = "simulation";
        attribute minMissionDurationHours : Real = 5.0;
        // 追溯关系 (relations):
        //   REQ-MISSION-ENDURANCE --satisfiedBy--> PART-POWER-CHAIN  (由功率链的整体能量效率保障)
    }

    // ---- ActionDefinition ----
    // description: 续航仿真工况。
    action def EnduranceSimulationRun {
        in cruiseSpeed : Real;  // unit: m/s
        out enduranceHours : Real;  // unit: h
        // 追溯关系 (relations):
        //   ACT-SIM-ENDURANCE --verifies--> REQ-MISSION-ENDURANCE  (该仿真工况验证任务级续航)
        //   ACT-SIM-ENDURANCE --verifies--> REQ-CRUISE-ENDURANCE  (同一仿真工况直接验证巡航续航指标)
    }

}
```

**确定性实测**（方案 2.4 的「可复现」）：

```
run1 sha256 = 32e23d5e14bb8e1e62e03cf82207c01a828dd02b1df0ab803f1492355e359e6c
run2 sha256 = 32e23d5e14bb8e1e62e03cf82207c01a828dd02b1df0ab803f1492355e359e6c
byte-identical: True
```

形态上的三点值得指出来：

1. **`REQ-CRUISE-ENDURANCE --refines--> REQ-MISSION-ENDURANCE`** 这条追溯关系落在文本里，
   评审时一眼能看到需求的分解链；
2. `part powerChain : PowerChain;` 里引用的是**被引用元素的 `name`**，不是 IR 的内部 id
   （内部 id 只出现在追溯注释里）——这样文本读起来是正常的 SysML，而不是一堆 `PART-XXX`；
3. 头两行明确写着「**事实来源是 IR JSON，别手改**」，把方案 3.2 的单一事实来源原则写进产物本身。

## 7. 第 6 步：回验 —— 本工程的选定方案实跑

**回验底座 = 内置轻量语法自查 lint + 声明抽取 + 与 IR 的元素级比对**
（选型理由与全部实测证据见 `docs/T0-调研结论.md` §2；实现见 `mcp-server/tools/sysml_lint.py`）。

```
$ python3 -c "... roundtrip_check(step4-final.ir.json, step5-generated.sysml) ..."
{
  "ok": true,
  "counts": {
    "irElements": 5,
    "textDeclarations": 10,
    "matched": 5,
    "missing": 0,
    "extra": 0,
    "mismatched": 0,
    "lintErrors": 0
  },
  "lint": { "lines": 41, "chars": 1610, "errors": 0, "warnings": 0 },
  "missing": [], "extra": [], "mismatched": [],
  "declarationsByKind": {
    "Package": 1, "PartDefinition": 1, "PartUsage": 1,
    "Requirement": 2, "Attribute": 4, "ActionDefinition": 1
  }
}
```

读法：

- **`matched: 5` / `missing: 0`** —— IR 里 5 个元素，文本里 5 个都找到了；
- **`extra: 0`** —— 文本里没有 IR 不知道的声明（说明没人手改过文本）；
- **`mismatched: 0`** —— `typeRef` 等字段两边一致；
- **`lintErrors: 0`** —— 括号闭合、注释与字符串完整、每条语句都正确终结；
- `textDeclarations: 10` 比 `irElements: 5` 多，是因为需求渲染时把两个阈值字段
  （`verifyMethod`、`minEnduranceHours`）落成了 `attribute` 语句——它们**属于该需求、不是独立模型元素**，
  回验已按「渲染在 `requirement def` 体内的 attribute 不参与元素级比对」处理（见
  `tests/test_lint_roundtrip.py::test_requirement_threshold_attributes_are_not_extra`）。

### 7.1 诚实披露：官方解析器与 PySysML2 都**没有**做到这一步

**这是本记录最重要的一段。** 方案 9.1 的验收判据写的是「文本被解析器成功解析」，
而本机实测结论是：**两个候选解析器都不满足本期判据**（详见 `docs/T0-调研结论.md` §2）。

用 PySysML2（T0 候选 B，已按 Apache-2.0 装上）对同一份文本实跑：

```
$ /tmp/pys2venv/bin/python docs/probe-pysysml2/parse_probe.py demo.sysml
--- demo.sysml: syntax_errors=5
    line 13:4  extraneous input 'requirement' expecting {'}', 'actor', 'attribute', 'comment',
               'connect', 'doc', 'item', 'package', 'part', 'port', 'ref', 'use', 'in', 'out', ...}
    line 16:40 mismatched input '=' expecting ';'
    line 17:43 mismatched input '=' expecting ';'
    line 22:4  extraneous input 'requirement' expecting {<EOF>, 'actor', 'attribute', ...}
    line 25:40 no viable alternative at input 'attributeverifyMethod:String='
```

**5 个错误全部可归因于 PySysML2 自己的语法缺口**，而不是模板形态有问题：

| PySysML2 报的 | 真实原因 |
| --- | --- |
| `extraneous input 'requirement'`（2 次） | 它的词法关键字表里根本没有 `requirement`——而需求是 MVP 的核心产物 |
| `mismatched input '=' expecting ';'`（2 次） | 它的 `attribute` 规则只有 `attribute ID : TYPE ;` 与 `attribute ID = VALUE ;` 两种形态，**表达不了「带默认值的类型化属性」** |
| `no viable alternative ... 'attributeverifyMethod:String='` | 同上（连方案 2.3 示例自带的 `attribute minEnduranceHours : Real = 4.0;` 也过不去） |

对照组（把同一个复现脚本跑在 PySysML2 能认的写法上）：`attribute capacityWh : Real;`（**无**默认值）
→ **0 错**。这组对照把问题钉死了：**它缺的是能力，不是我们写错了。**

**官方 pilot implementation（Java）**：`java -version` → `Unable to locate a Java Runtime`，
本机无 JVM、无 Maven/Gradle → **根本无法执行**。

**所以本期的诚实口径是**：

- ✅ 我们**实际做到**的是：文本由固定模板生成 + 通过内置轻量 lint（带行列定位）+ 与 IR 完成元素级比对；
- ⛔ 我们**没有做到**的是：「文本被官方 SysML v2 解析器成功解析」——这一条**留待二期**，
  届时按 `docs/T0-调研结论.md` §2.5 的薄适配层接入；
- ⚠️ 因此**绝不能**对外宣称「生成的文本已通过官方解析器验证」。方案 10.1 说「架构抬下限不抬上限」，
  这里就是把下限的口径如实收窄，而不是把没做过的验证说成做过。

## 8. 第 7 步：汇报（智能体对用户说的话）
