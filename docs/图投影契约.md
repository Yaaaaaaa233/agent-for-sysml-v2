# 图投影契约（`sysml-graph/v1`）

> 状态：v1（2026-10-19）。实现：`mcp-server/tools/graph.py`；测试：`tests/test_graph.py`。
> 角色：Q2「图形化侧边栏」的**数据契约层**。只做 `IR JSON → 图数据` 的确定性投影，
> **不画图、不做布局、不写回 IR**；IR 仍是唯一事实源。

## 1. 为什么不动 IR schema

IR（`sysml-ir/v1`）只描述模型语义，没有坐标/视图/标注概念；把图信息塞进 IR 会牵动
validator/generator/parser/lint/文档全链路（升 schema v2 成本高、且污染模型事实）。
因此图投影是**只读派生层**：同一份 IR 可随时重算，IR 不变则图逐字节不变。

## 2. 顶层结构

```json
{ "schema": "sysml-graph/v1",
  "modelRef": { "package": "CoaxialOctoRotor", "elementCount": 34,
                "relationCount": 20, "contentSha256": "<64 hex>" },
  "views": [ { "viewId": "structure-root", "kind": "GeneralView", "scope": "…",
               "title": "…", "description": "…",
               "nodes": [ … ], "edges": [ … ], "groups": [ … ] } ],
  "stats": { "viewCount": 4, "nodeCount": 56, "edgeCount": 34,
             "elementsByKind": {…8 种…}, "relationsByType": {…5 种…} } }
```

- **节点**：`id / kind / label / owner / parent / attrs`。`parent` = owner 在本视图内时取其 id
  （视图内的父子树），否则 `null`；`attrs` 只挑展示需要的字段（description、quantity、
  typeRef/typeName、text/acceptanceCriteria、defaultValue/unit、expression/parameters…）。
- **边**：`id / kind / source / target / label`，可选 `rationale`。
  边 kind 枚举：`typeRef`、`connection`、`connects`、`refines`、`decomposes`、
  `satisfiedBy`、`verifies`、`transition`；`connection` 的 label = `flowKind`，
  追溯边的 label = 关系 type，`transition` 的 label = trigger（guard 附 `[if (...)]`）。
- **分组**：`{groupId:"kind:<Kind>", label, kind, nodeIds, count}`，按节点 kind 分，
  给前端「按类别」树用；「按层级」树直接用节点的 `parent`。

## 3. 四个视图（`VIEW_ORDER` 固定）

| viewId | kind | scope | 节点 | 边 |
| --- | --- | --- | --- | --- |
| `structure-root` | GeneralView | package | 全部元素（owner 层级树） | `typeRef` + `decomposes` |
| `ibd-power-chain` | InterconnectionView | `PART-POWER-CHAIN`（缺失时取 Connection 的 owner） | scope 元素 + 其子树内 PartUsage | `connection`（sourceRef→targetRef）+ 未被覆盖的 `connects` |
| `requirements` | RequirementView | package | 全部 Requirement + 追溯边另一端的外部节点 | `refines / decomposes / satisfiedBy / verifies` |
| `state-flight-modes` | StateView | StateDefinition id | 容器节点 + 合成状态节点 `<id>::<state>` | `transition` |

- 状态图：`attrs.initial=true` 标注初始态（不额外造边）；容器节点 attrs 只有 description。
- IBD：同一 `(source,target)` 的 `connects` 追溯边若已被正式 `Connection` 覆盖则不重复出边；`quantity` 等展示属性在节点 attrs 上。
- 需求图：`satisfiedBy`/`verifies` 的另一端不是 Requirement 时，作为外部节点并入视图，
  否则这两类最关键的追溯边会画不出来；**边只来自 IR 已写的关系，不做语义推断**。

## 4. 确定性规则

1. `views` 按 `VIEW_ORDER`；2. `nodes` 按 `KIND_ORDER`（8 种 IR kind，合成 `State` 置末）
再按 `id` 升序；3. `edges` 按 `(kind, source, target, id)` 升序，边 id 由投影器合成
（`<kind>:<source>-><target>#<n>`，不透明、稳定、唯一）；4. 不依赖 JSON 对象键序与
`elements` 数组顺序；5. `contentSha256` = IR 规范化 JSON（`sort_keys`、`separators=(",",":")`、
`ensure_ascii=False`）的 sha256 —— 可直接当修订号，用来判断图/文/标注是否同源。

## 5. 前端如何消费

```bash
python mcp-server/tools/graph.py --input <ir.json>            # 全量图 JSON → stdout
python mcp-server/tools/graph.py --input <ir.json> --view requirements   # 单视图调试
python mcp-server/tools/graph.py --input <ir.json> --output graph.json   # 写文件
python mcp-server/tools/graph.py --input <ir.json> --check    # 只校验，输出 ok/errors
```

输出恒为 `{ok, graph, errors, warnings}`；建议前端轮询 `--check`/`--output -` 的
`contentSha256`，变化才重取图；按 `viewId` 切 canvas、按 `groups`/`parent` 建树、
按 `edges.kind` 上不同线型。`--check` 输出 `{ok, input, errors, warnings, schemaLayer}`。

## 6. 错误契约与已知限制

- 非法输入（非 JSON、顶层非对象、schema/字段/引用不合法）**不抛异常**：
  `{ok:false, graph:null, errors:[{code, element, message, pointer?}]}`，错误码沿用 `validate_model_json`；
  投影器自身错误用 `E-GRAPH-INPUT` / `E-GRAPH-VIEW-UNKNOWN` / `E-GRAPH-OUTPUT` / `E-GRAPH-INTERNAL`。CLI 失败退出码 1。
- 已知限制：① 无坐标/布局，位置由前端布局器（如 ELK）决定；② IR 无 port/interface，
  IBD 用 `flowKind` 近似；③ 状态机视图只展示一个状态机（优先 `STATE-FLIGHT-MODES`，
  否则 id 最小者）；④ 需求视图的外部节点只为补全端点，不代表额外语义；
  ⑤ `Constraint.expression` 是自由文本，本层不求值、不做量纲检查。
